# 发布准备与许可证状态

当前版本：`1.2.0-beta.7`。维护者已于 2026-10-03 要求继续完善并推送到现有 GitHub 仓库，许可证决定保持不变。发布前验证与未验证项见 [本版记录](verification-beta7.md)，beta.6 见 [历史记录](verification-beta6.md)；远端状态以对应提交和 Actions 结果为准。源码推送不表示创建了 Release 或标签。

## 已决定不添加许可证

本仓库不添加 MIT、Apache-2.0、The Unlicense、CC0 或其他 LICENSE 文件。`package.json` 保留 `private: true` 和 `license: UNLICENSED`，表达 npm 包不公开发布且没有声明分发许可；**UNLICENSED 不等于 The Unlicense**。`private: true` 阻止 npm 误发布，并不决定 GitHub 仓库的公开/私有状态。

GitHub 不要求仓库必须选择许可证。没有许可证时，默认版权规则仍然适用；GitHub 条款允许的公开查看和平台内 fork，不等于一般性的复制、修改、再分发或商业使用许可。说明见 [GitHub 官方许可证文档](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)（2026-10-02 核对）。具体权利还取决于适用法律及另行授权，本文不是完整法律意见。

因此 README 可以描述“规范包”“公开仓库”“使用方法”，但不声明“采用开源许可”“无限制使用”“任意商用”或“公共领域”。提示词和教程说明如何工作，不作为额外许可文本。若维护者未来希望主动允许其他人复用或商业使用，应另行明确授权边界，再同步元数据和文档；当前任务不替维护者选择。

第三方依赖、引用、模板、图片、代码仍各自遵守来源许可和声明；本仓库不添加许可证不能抹去第三方义务。接受外部代码前明确其来源与授权，不默认存在 CLA。历史版本记录中的“许可证待定”描述当时状态，不改写历史为今日决定。

## 本地文件与 GitHub 仓库的区别

本地 `git init`、文档齐全、配置了 CI，均不等于已经上传。真正上传需要明确账号/组织、仓库名、可见性、分支、拟提交内容和远端地址；不能使用猜测出来的地址或静默把私有资料设为公开。

维护者可以选择公开一个注明限制的测试版。公开草稿、发布测试版和推荐生产采用是不同成熟度，不能因为允许上传就省略风险披露；对示例的当前依赖风险与评测缺口，保留 [beta.3 历史验证报告](verification-beta3.md) 和 [beta.4 验证报告](verification-beta4.md)。

## 发布准备顺序

1. 确认范围。先查看当前差异、未跟踪文件、已有远端及历史；没有提交或远端时如实说明，不捏造基线。
2. 审核内容。检查拟提交文件和将被发布的历史范围是否包含秘密、私人路径、对话、测试产物或未授权第三方材料。`.gitignore` 不会清除已经追踪或进入历史的内容；基础正则扫描也不是完整秘密审计。
3. 验证候选。运行下方适用检查，区分本地结果、历史结果、远端尚未运行，以及不能完成的环境验证。版本和发布说明与真实结果一致。
4. 确认目的地。只有用户明确要求上传时，才核对所有者、仓库名、可见性和认证账号。请求用户通过安全机制完成认证，不要求把访问令牌写入文档或 URL。
5. 执行已授权上传。逐项审查拟提交文件，不盲目 `git add .`；保留已有修改，不强推、不改写历史、不替换已有远端，除非这些动作另有明确授权。
6. 上传后核验。查看实际提交与公开内容，取得真实仓库 URL；如执行了 CI，读取实际结果。推送成功不等于所有 job 通过，CI 成功也不等于已经创建 Release。

只要求完善仓库文档的任务停在第 3 步。发布准备提示词见 [11 GitHub 发布准备](../prompts/11-release-preparation.md)，不会因为复制这段流程自动授权远端动作；以前上传的结果不能代替本版发布与远端验证。

## 发布前清单

- 运行 `npm run check`，检查真实退出码；如支持的其他操作系统尚未验证，明确记录。
- 安装示例依赖后运行 `npm run check:examples` 和 `npm run test:negative`；查看 `npm audit` 的实际结果，不把构建通过当安全审计通过。
- 按 [Agent 评测](../evals/README.md) 留存独立任务的机器验收与人工证据；额度不足或环境中断标记未完成，不记为成功或抹去失败。
- 在 GitHub 实际运行仓库 CI，确认 Linux/Windows、Node.js 22/24 的结果，而不是只检查 YAML 存在。
- 选择一个代表性业务项目，验证规则采用、一次真实开发任务及适用检查，记录范围；本仓库单元测试不能替代这一步。
- 检查待提交文件，不包含 `.tmp/`、凭证、个人路径、聊天记录、临时备份和未授权上游内容。基础正则校验不替代人工检查。
- 复核无 LICENSE 的既定决定、UNLICENSED/private 元数据，以及第三方许可；真正上传前明确仓库所有者、名称、可见性和内容范围，补充实际链接，不写虚构下载地址和通过徽章。
- 对照 [版本记录](../CHANGELOG.md) 说明新增内容、行为变化、兼容性和已知限制。
- 检查 [完整规范流](agent-workflow.md)、[提示词目录](../prompts/README.md) 与可选模板的导航；纯文档检查通过不等于 13 类提示词都完成现实 Agent 评测。
- Actions 已固定到查证过的发布提交；正式发布及后续升级时重新检查版本、兼容性与上游变更，不改成未经核对的提交或浮动标签。
- 仅在维护者明确要求后执行远端创建、推送与发布；准备文件不自动完成这些动作。

CI 使用普通 `push` / `pull_request` 事件、只读仓库权限，不使用 `pull_request_target`，不自动发布、上传业务资料或使用部署密钥。当前固定 [checkout v7.0.1 的发布提交](https://github.com/actions/checkout/commit/3d3c42e5aac5ba805825da76410c181273ba90b1) 和 [setup-node v7.0.0 的发布提交](https://github.com/actions/setup-node/commit/820762786026740c76f36085b0efc47a31fe5020)；固定版本不等于完整安全审计。

示例 job 额外固定 [setup-java v6.0.1 提交](https://github.com/actions/setup-java/commit/de7274f081f381c8f8158605e0321c36c376e2e6)，配置 Java 17 / Node.js 24，在 Linux 与 Windows 上运行正反例；配置只描述目标矩阵，具体提交是否通过须查看实际执行。本版实际执行与重新依赖审计见 [beta.7 验证记录](verification-beta7.md)，历史范围见 [beta.6](verification-beta6.md) 和 [beta.3 报告](verification-beta3.md)。

## 版本与兼容性

修正文案且不改变规则意图可作为补丁；新增可选规则或功能可作为次版本；移除技术栈、变更 CLI 或收紧既有默认规范时说明迁移影响，必要时提升主版本。预发布版本用于收集实际项目反馈，不宣称已经普适。

更新版本时同时改 `package.json`、`SKILL.md`、项目画像模板、来源说明、README、本文和 CHANGELOG。校验器检查这些位置的一致性。已采用项目按差异合并，不直接覆盖历史规则。

GitHub 下载的仓库文件夹可以直接供 Agent 读取。分发当前版本时保留 SKILL 及其链接的配套文件，排除 `.git/`、`.tmp/`、`node_modules/`、`target/`、`dist/` 和其他运行产物，重新验证本地链接与导出；不要只分发一个脱离配套文件的 SKILL.md。精简发行包需要另外定义和测试文件清单，当前未提供独立精简打包器。
