# API、数据契约与安全

仅在任务涉及相应契约、数据或风险时读取，不给普通样式修改加载整套安全审计流程。

## 实现前确认

- 接口路径、方法、输入输出、校验、权限、分页、错误与兼容性；字段含义、缺失/null/空值的区别。
- 新 REST 默认小写资源路径，如 /api/orders；JSON 默认 camelCase，数据库默认 snake_case；既有契约优先。
- 金额采用精确表示并明确币种、单位和舍入；时间字段区分时间点、日期与时长，明确时区。
- 沿用一种响应体系；HTTP 状态表达实际结果，不全部返回 200，不叠加 Result/ApiResponse 多层包装。
- 排序字段允许列表，分页、批量、上传尺寸有界；公开契约变更需兼容过渡。

## API-01 用契约表消除猜测

新增或重要变更的接口至少明确下表中的相关项；可以写入已有接口文档或任务说明，不强制每个接口新建 Markdown 文件。

| 契约项 | 正例 | 反例 |
| --- | --- | --- |
| 输入 | quantity 的类型、范围及必填性明确 | 任意 Map 接收全部字段后透传到持久层 |
| 缺失与空值 | 区分 PATCH 未提供字段与明确清空 | 将未提供、null、空字符串全部静默转成 0 |
| 输出 | 只暴露客户端所需字段与明确精度 | 原样序列化实体的密码摘要、内部状态或关系对象 |
| 权限 | 服务端验证身份、资源归属和允许操作 | 请求传什么 tenantId 就访问哪个租户 |
| 分页与排序 | 上限、允许排序字段、稳定顺序有定义 | 任意排序 SQL、无界 pageSize |
| 错误 | 状态码和稳定业务错误分类对应真实结果 | 所有错误 HTTP 200，客户端靠匹配中文消息判断 |

上述正例仍服从项目已发布的协议。不能为了统一格式，突然给全部旧接口套新的响应包装或改字段大小写。

## API-02 错误、重试与幂等是同一合同的一部分

错误响应沿用项目定义，面向用户的信息与内部诊断分离，不返回堆栈、SQL 或秘密。错误分类要支持调用方决定是否修正输入、重新认证、稍后重试或停止；不能只给一个不可区分的“系统错误”。

需要防重复的创建/支付等操作定义幂等作用域、相同键不同参数的行为、结果复用与有效期，服务端持久化或并发约束必须支持该定义。隐藏按钮、禁用提交和单进程内存标志不替代服务端保障。

公开字段、状态值和错误码的兼容变更补读 [变更管理](change-management.md)；验证输入边界、拒绝和重复请求见 [测试规范](testing.md)。

## 数据与失败路径

- 参数绑定而非 SQL 值拼接；动态标识符限定允许范围。
- 通过项目既有迁移机制改变数据库，已在共享环境执行的迁移不随意改写。
- 唯一约束、并发一致性和幂等不能只靠先查再插；避免 N+1 和无界读取。
- 明确回滚、传播、事务调用路径；非幂等操作没有保护时禁止自动重试。
- 重试有条件、次数上限、退避；跨系统一致性沿用项目方案，不随意引入分布式事务平台。

## 安全与日志

- 可信服务端完成鉴权、授权、租户与对象归属校验；隐藏按钮不是权限控制。
- 密钥与生产凭证不进仓库、日志、前端或小程序；避免不必要的个人敏感数据。
- 参数化或结构化日志，必要时记录关联 ID；业务审计与运行日志分别定义访问和保留策略。
- 上传、外部 URL 和富文本按场景防路径穿越、SSRF、XSS；不为测试关闭鉴权或证书验证。
- 测试不得连接生产数据；按变更风险验证拒绝路径、重复提交、回滚、并发和跨租户隔离。

## API-03 契约只有一个受维护的源头

触发：新增/调整 OpenAPI、SDK、公开 DTO 或接口文档。先确认项目是 schema-first、code-first 还是人工维护合同，记录权威文件、实际 OAS 版本、生成器/校验器和消费者；不为统一文档改变既有生成方向。

写代码前明确 operationId/操作名的唯一性与稳定性、字段类型/范围/必填/可空、请求和响应的区别、身份要求及真实错误结果。示例不得夹带真实个人数据或秘密。共享 schema 复用只限相同语义，不把数据库实体直接当所有输入输出；避免为修改一个接口无意改变所有引用者。

生成代码从权威源重建，不手改生成文件；非生成路径同步契约、实现与测试。按项目实际版本校验 schema、解析引用、生成客户端并验证兼容变更，不能只检查 YAML 可解析。OAS 版本和工具支持不一致时先核对，不能把一个版本的 nullable 等语法直接复制到另一个版本。

正例：保持现有 code-first，新增响应字段同步注解、生成契约及消费者边界测试。反例：手改自动生成的 OpenAPI，下一次构建覆盖；凭接口名推断公开访问；省略所有失败响应却称合同完整。未接入契约检查时在计划中记录，不假装框架自动保证一致。

## SEC-01 敏感字段在生成前定义用途和流向

触发：新增/调整个人、凭证、支付或其他项目认定的敏感数据。按业务内容与组合风险识别，不仅凭 email、phone 等字段名；普通商品字段不强制走完整隐私评审。技术分类不是法律合规结论。

在已有契约或画像里记录相关项，不为每个字段创建文档：

| 设计项 | 写入前要确定 | 核验例子 |
| --- | --- | --- |
| 收集目的与最小化 | 为什么需要，能否不收集/不存储 | 列表展示不需要的号码不出现在响应 DTO |
| 允许流向 | 哪些角色可读写，能否进入客户端、导出、缓存和日志 | 未授权/跨租户读取与批量导出被拒绝 |
| 保护与保留 | 原值/掩码/派生值、实际访问控制、保留与删除依据 | 异常日志不含原值；清理覆盖约定副本 |
| 测试与可观测性 | 合成数据、脱敏诊断、合法关联标识 | 回归报告和截图不包含真实用户记录 |

掩码、散列、加密与匿名化不是同义词；UI 遮挡不防止接口返回原值，字段注释不实施访问控制，可关联的散列也不能直接称匿名。具体保护方案按威胁、数据用途及项目机制确定，不在前端保管服务端秘密，不编造统一保留天数或强制全部表加审计字段。

正例：客户列表只返回必要掩码，特权详情另做服务端授权和拒绝测试。反例：接口返回完整原值，仅页面替换星号；为方便调试把请求体和令牌整体写日志。相关高风险变更按 [风险与证据](quality-gates.md) 选择验证，缺环境如实标记。
