# 命名、接口与继承设计

触发：新增或改名类型、接口、方法、字段、页面和组件。默认规则仅在项目没有已确认约定时采用；涉及公开字段或持久化映射时先核对消费者，而不是批量改名。

## NAME-01 按对象选择命名规则

| 对象 | 默认正例 | 反例或需说明的写法 |
| --- | --- | --- |
| Java 包 | com.example.order | com.example.Order、order-service；包前缀必须来自真实项目 |
| 类型 / 公共类型文件 | OrderService / OrderService.java | Order_service / Service2.java |
| 方法 / 字段 / 参数 | calculateTotal、orderId、retryCount | handleData、data1、flag2 等没有领域语义的名字 |
| 常量 / 枚举项 | MAX_RETRY_COUNT、PENDING_PAYMENT | 用常量命名掩盖可变运行状态 |
| 普通业务目录 | order-history | 跟 Java 包、框架保留目录一律套用 kebab-case |
| Vue 组件 | OrderCard.vue | 一个订单卡片叫 Common.vue |
| 组合式函数 | useOrderList / useOrderList.ts | 无组合式语义的通用工具都加 use 前缀 |
| 数据库字段 / JSON 字段 | order_id / orderId | 因本表改掉已发布的 order_id JSON 契约 |

已有 DTO/VO/DO、缩略词及组件命名方案可以保留，但同一边界内一致。第三方协议、框架保留名和生成文件以其真实约束为准，不做全仓机械替换。

核验：技术栈对应的命名检查、文件与类型对应关系、调用处及序列化契约测试。命名正则只能检查形状，不能证明领域含义正确。

## NAME-02 字段表达类型、单位和状态

约束：明确可空性、单位、精度和状态含义；不要把未知状态强行写成 false 或 0。默认用肯定形式命名布尔属性，如 enabled、visible；避免 isNotDisabled 一类双重否定。

JavaBean 的字段、访问器与 JSON 名称需区分：例如 enabled / isEnabled() / enabled；不可因访问器前缀就改成另一公开字段。Nullable Boolean、代码生成器和序列化器按实际配置验证，不假设 getter 推导完全相同。

正例：timeoutMillis 或明确类型的 Duration；枚举 OrderStatus 表达有限状态。反例：含义不明的 timeout=30；若干布尔位组合出无定义订单状态。是否向名称加入单位由类型系统和项目约定共同决定，不能要求 Duration 也重复编码单位。

## NAME-03 方法名体现行为和失败语义

默认用领域动词，如 submitOrder、cancelOrder、findOrderById。读取方法不隐藏扣费、提交或写库；一个布尔参数若改变整个业务路径，考虑显式命名的操作或配置对象，而不是增加更多 true/false 参数。

正例：取消订单有明确前置状态与结果。反例：getOrder 实际标记订单已付款；process(order, true, false, true) 的含义只能靠实现猜。

get/find、找不到时返回空还是抛异常，必须服从本项目公开契约，不由名字凭空推断。必要时注明副作用、失败条件和单位，而不是给每个简单 getter 添加重复注释。

## TYPE-01 先证明需要接口，再创建实现

约束：接口表达稳定的调用能力或边界，不只为凑齐文件。默认已有单实现内部 Service 不额外生成同名接口；真实扩展点、跨模块契约或隔离外部系统时可以建立接口。

正例：PaymentGateway 隔离支付系统，实现名说明渠道或适配方式。反例：每个类都自动生成 I 开头接口与 Impl，只有一条委托且没有设计目的。已有团队统一接口模式属于合法例外，应保持局部一致，不顺手删除。

接口的输入输出不能泄漏不必要的 ORM 类型、HTTP 对象或前端组件实例。核验调用方向、公开类型和测试替身；不能仅因“可 mock”就宣称抽象合理。

## TYPE-02 继承是可替代关系，不是复制代码的捷径

默认优先组合；只有子类能遵守基类契约和生命周期时使用继承。覆写不得暗中加强调用前提、削弱结果保证或依赖未声明的调用顺序。

正例：遵循已有扩展协议的实现，并用契约测试验证。反例：所有 Controller 继承持有数据库、缓存、登录态的 BaseController；为了访问字段把所有成员改成 protected/public。

框架要求的扩展基类可以使用，但只覆盖其声明的扩展点。字段采用满足需求的最小可见性；不能以一条通用规则禁止所有框架继承或强制所有类 final。

## NAME-04 注释与 TODO 有信息量

注释解释限制、取舍和不明显的业务原因，不逐行复述代码。公开接口说明输入边界和副作用；临时 TODO 包含可定位的问题或退出条件，不虚构任务编号。

正例：说明舍入方式为何必须与账单对齐。反例：给每次赋值写“赋值”，或留下没有范围的“以后重构全部”。修改行为时同步旧注释，删除已失效说明。
