# 变更、依赖与规则维护

触发：新增依赖、模块/契约变更、规范例外、提交或发布准备。这里不要求普通小修复创建完整设计文档，也不授予提交、推送或部署权限。

## CHANGE-01 变更范围可解释

约束：功能、迁移和纯格式化尽量分开，不夹带无关框架升级或整仓重构；保留用户已有修改。新增架构决策只记录影响长期边界的选择，不给每个新方法写 ADR。

默认提交/PR 描述包含目的、主要行为变化、兼容性、实际检查和未验证项。分支、提交前缀及合并方式沿用团队规则，不强制所有项目采用一种 Git 流程；不能自动重写共享历史。

正例：新增查询接口时只修改相关模块、契约和测试。反例：以“统一风格”为由同时替换 ORM、调整全部包名，再声称是小功能。

## DEP-01 依赖有必要性和兼容证据

约束：新增依赖先查现有能力和实际需要，核对运行时、框架与目标平台；从可信来源确定版本，不猜一个版本号填入清单。保留项目管理方式及相应锁文件。

正例：缺少必要能力时添加兼容依赖，记录用途及影响；同仓不同模块按现有依赖管理策略更新。反例：解决一个简单格式问题引入完整平台；仅为修一项警告批量升级所有大版本。

业务依赖与测试/构建依赖按实际运行需求区分。检查许可证和所需声明，不能把“能下载”当作可随意再分发；这不要求每次小改做完整供应链审计。

## CHANGE-02 公开契约按消费者评估

约束：重命名 API 字段、改变类型/可空性、错误码、状态枚举、分页语义或组件事件之前，确定受影响消费者及兼容策略。新增字段也可能影响严格解析器、签名或快照，不能一律宣称兼容。

正例：保持旧字段/路径的兼容窗口，明确废弃和迁移条件。反例：后端类型检查通过就直接改掉移动端已使用的字段；将业务失败改成成功状态码以迁就客户端。

契约、实现、示例与测试一起维护。内部私有对象无需按公开 API 建立冗长流程，但也不能假定名字叫 internal 就没有跨模块使用者。

## RULE-01 规则的层级与例外明确

本包的“约束”在项目采用后执行；“默认”可以由正式项目选择替换；“建议”按任务权衡。平台/框架真实要求须另外核验，不能把团队偏好描述成语言标准。Agent 自身指令优先级不由本包改写。

例外记录规则或条目、限定路径、原因、批准依据、补偿验证及复审条件；没有真实批准记录就标待确认，不能虚构负责人或审批。允许在项目画像中记录，不强制每个例外单建文件。

正例：既有框架要求的基类在指定模块保留并验证契约。反例：一个遗留文件违规就关闭全仓检查；把已有偶然写法当成所有新代码的正式标准。

## RULE-02 规范升级采用差异合并

约束：记录项目采用版本和团队调整；新版本先比较变更，再合并受影响规则，不覆盖现有项目入口、例外及实际命令。草稿导出工具不是升级器。

技术栈、目录、构建方式或公开契约变化时更新对应画像证据；不必每次开发重扫全仓。新增规则应有适用场景、正反例或判断依据和验证方式，删除已无作用的重复说明，不无限增加上下文。

完成标准：相关文档链接有效，任务涉及的规则已明确，实际检查及缺口如实报告；不能把规则文件变多当作规范效果变好。
