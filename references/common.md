# 开发前约束

用途：采用本包后的编码入口。项目正式规则、现有一致实现与本次授权优先；本包不是整体重构的理由。

## 下笔前确定什么

| 对象 | 先确认 | 默认选择，项目无既定约定时使用 |
| --- | --- | --- |
| 目录、包、文件 | 业务归属、已有位置、同类文件和引用 | 按职责或业务模块组织；不生成无用空目录 |
| 类、接口、基类 | 单一职责、调用者、可见性、真实扩展需求 | 类型 PascalCase；优先组合；不强制 Service 一对一接口 |
| 方法、字段、参数 | 领域含义、数据边界和兼容性 | camelCase；常量 UPPER_SNAKE_CASE；避免含糊 data/info/flag |
| API、表、公开 DTO | 类型、缺失/null、权限、错误及兼容性 | 沿用项目响应体系与迁移机制 |
| 页面、组件 | 路由、目标平台、输入输出、状态和请求责任 | 沿用工程形态；不混用原生小程序与 Vue 路由 |

新增模块、公开接口、数据库迁移或重要架构变化时，简要说明位置、契约和验证方法。小修复直接按现有模式完成，不创建形式化审批流水或长设计书。

## 工程蓝图如何在写入前生效

专项规范中的目录树是默认候选；项目画像确认的角色映射才是日常依据。首次采用记录“职责 -> 真实路径 -> 命名 -> 允许/禁止依赖 -> 注册/测试关联”，已有项目映射现状而非搬迁，新项目选定后保持一致。没有同类先例或选择冲突时仅确认会影响本次实现的项。

创建功能时，在首次写入前给出简短清单，例如“订单 HTTP 入口放既有 web，应用用例放 application，复用 persistence；不建新 service 包”。复杂功能可用表格，局部修复一句话即可，不要求每个文件重新审批。

“接口层”可能是 Controller/Resource、客户端 API 或语言 interface，必须结合技术栈说明；“服务层”也不能同时混用客户端传输、业务编排与后台用例的含义。复用一个既有角色比复制一份标准目录更重要。

## 从需求到交付

1. 先确认任务范围、相关工作区差异、真实项目证据和可观察的验收条件。
2. 在首次相关写入前确定上表适用项；关键业务语义、授权或不可逆变更不明时先确认，其余安全工作继续。
3. 以最小变更实现，缺陷与关键边界建立有效回归，不把最终自述当作写前约束已经执行的证据。
4. 运行实际检查并核对测试发现与覆盖；分别报告通过、失败、环境阻断、未运行、未接入和不适用，不自动部署或发布。

这些是决策顺序，不要求每一步审批或单独生成文件。用户要求只读审查时不改代码；检查命令也可能有写入或外部副作用，需符合当前授权范围。

## 不可跳过的边界

- 保留用户已有修改；不覆盖、回滚或顺手清理无关内容。
- 新建前寻找同类实现；不同时建立 controller/service 与 DDD 等两套平行架构。
- 只创建真实需要的文件。源代码、测试、生成代码、资源和构建产物分开。
- 路径引用与实际大小写一致；不手工编辑依赖目录、生成文件或构建产物。
- 必要改名同步处理 import、路由、配置、资源和测试，公开路径先评估兼容性。
- 不擅自升级框架、切换包管理器、替换 ORM、开启云服务或改变发布方式。
- 未知版本、包名前缀、目录规则和命令从项目查证；确需用户决策的事项才询问。

## 适用与例外

“必须/禁止”在项目采用后是硬约束；“默认”可被团队约定替换；“建议”按需求取舍。规则冲突说明依据，例外记录影响范围、理由和批准依据；不得全局禁用解决局部问题。

最终报告只需结果、实际验证、未验证项和重要兼容性变化。规则减少错误，但不能保证每次生成正确或满足全部企业合规要求。
