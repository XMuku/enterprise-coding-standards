# 测试组织与有效验证

触发：行为变更、缺陷修复、新增测试或接入检查。采用项目已有测试框架和兼容版本，不为使用本规范迁移测试栈。

## TEST-01 测试要被发现，并描述行为

约束：测试放在实际运行器扫描的路径，命名符合其配置。默认沿用项目的 OrderServiceTest、order.spec.ts 等形式，不规定所有框架必须使用同一种后缀。

正例：测试名称表达“已取消订单不能再次付款”，并被真实命令执行。反例：创建 TestOrder2 文件，只靠文件存在或“0 个测试成功”证明覆盖。

Java 源码和测试包保持可理解的对应关系；前端测试可就近或集中放置，以已有模式为准。选择框架能力时查阅对应版本的 [JUnit 文档](https://docs.junit.org/current/user-guide/) 或实际前端运行器文档，不把最新示例当升级授权。

## TEST-02 断言可观察结果，不只是执行过

约束：对输出、状态变化、错误语义或重要副作用做有效断言。缺陷修复优先加能重现问题的回归测试，再验证修复；难以自动重现时说明限制并记录人工步骤。

正例：断言库存不足时拒绝创建，库存和付款记录未改变。反例：仅断言 mockedService 调用一次，完全 mock 掉需要验证的业务；只检查代码里出现某个注解。

依赖交互本身就是契约时可以断言调用，但不能把交互次数替代数据库约束、事务回滚或权限效果。生成配置检查应验证实际失败路径，不只检查某段文本存在。

## TEST-03 按变更风险选择层次

| 变更 | 至少考虑的验证 | 不足的替代品 |
| --- | --- | --- |
| 纯计算/状态转换 | 边界输入、错误状态、精度 | 只有一组正常数据 |
| API / 字段 | 请求校验、响应结构、错误与兼容性 | 只测方法返回非空 |
| 权限 / 租户 | 未授权、其他租户、对象归属拒绝 | 隐藏按钮的 UI 截图 |
| 数据 / 事务 | 实际持久化行为、约束、失败回滚 | mock 数据库后宣称事务正确 |
| 并发 / 幂等 | 重复与并发调用、不重复产生副作用 | 先后两次串行调用就宣称线程安全 |
| 页面 / 组件 | 加载、空、错误、交互及目标平台 | 只编译 H5 就认为其他端正常 |

不要求每次小改都运行所有层次。说明选择依据，沿用既有覆盖门槛；不为追求数字编造无断言测试，也不统一要求所有项目 100% 覆盖。

## TEST-04 隔离时间、状态和外部环境

约束：测试不得依赖生产凭证、真实用户数据、执行先后顺序或不受控公网结果。时间、随机数和外部响应按现有依赖边界控制；并发测试使用明确同步点和有界等待，不靠随意 sleep 猜时序。

正例：独立测试数据、可控时钟、受控服务替身或隔离数据库。反例：共享同一个可变全局账号；失败后无限重试直到通过；读取个人电脑绝对路径作为固定夹具。

外部沙箱的端到端验证可以单独运行，但必须说明环境、成本和清理范围。清理只处理本次拥有的数据或目录；不能对任意配置路径递归删除。

## TEST-05 如实记录失败和未执行

记录实际命令、工作目录、结果及未覆盖的目标。区分历史失败与本次回归，不扩大忽略目录、不关闭规则、不把测试失败转成成功退出码。

测试暂时隔离时记录具体原因、影响范围和恢复条件；不能假装已通过。构建、单测、架构检查和目标端交互分别报告，不互相替代。
