# 公共能力、业务功能与产品入口

触发：新模块、跨模块复用、页面状态拆分、产品入口调整或明确的架构迁移。源自本包整合的通用框架规范，目录名是可选方案；已有 Java 分层、DDD、uni-app 或小程序结构按职责映射，不为了三个名字搬动整个项目。

## ARCH-01 三类职责先于目录名称

| 职责 | 可选目录名 | 可以包含 | 不应包含 |
| --- | --- | --- | --- |
| 公共基础能力 | commons / shared / infrastructure | 稳定的网络传输、日志、配置、存储适配、通用 UI | 某业务的规则、页面、私有状态和路由决定 |
| 业务功能 | features / 既有业务模块 | 自有模型、用例/服务、页面、展示状态、私有组件与资源 | 对产品壳的反向依赖、其他模块私有实现 |
| 产品/应用组装 | products / app / entry / bootstrap | 入口、导航、依赖装配、设备适配、产品壳与资源 | 与入口无关的复杂业务规则或数据访问 |

先记录实际路径、模块类型和消费者，再决定是否需要新目录。产品壳可以组合 feature；feature 可以使用公共能力；公共能力不能反向 import 业务或产品；feature 不能 import 产品入口。

正例：应用入口注入请求客户端并组装订单页；订单用例只依赖稳定数据访问契约。反例：公共 HTTP 客户端 import OrderPage 并直接跳转该页；Service 持有入口组件实例。

此图描述典型前端组装方向。Java/六边形项目的领域与适配器依赖采用项目既有约束，通过依赖倒置实现能力接入，不将“feature 可依赖 commons”当成允许领域层随意依赖基础设施。

## ARCH-02 公共抽取需要共同语义

“两个使用者”只提供候选信号。抽取前确认职责、语义、生命周期、类型契约、调用方和依赖方向确实一致。基础网络/日志可以先有一个使用者；绑定业务规则的代码即使有多个使用者，也优先放在负责该领域的模块，通过公开契约共享。

| 对象 | 默认归属 | 提取条件 |
| --- | --- | --- |
| 订单价格、登录流程、库存规则 | 所属业务模块 | 多消费者使用其明确公开契约，不改名塞到 utils |
| 传输错误、重试预算、日志接口 | 既有基础能力 | 和具体业务解耦，失败策略清晰 |
| 页面表单和加载状态 | 所属 feature/页面 | 跨页面确有相同状态所有者时才提升 |
| 通用确认框、空态、按钮 | 局部起步或既有公共 UI | 输入/事件稳定，样式和平台约束一致 |
| Mock 与测试数据 | 测试边界或明确 mock adapter | 可与生产实现区分，不能误打包秘密或真实用户数据 |

正例：两个模块调用订单模块公开的查询接口。反例：为避免跨模块访问，把所有订单 Repository 和 DTO 搬到公共数据包；把“未来可能复用”作为唯一依据造通用基类。

## ARCH-03 展示与业务按职责衔接

采用 MVVM 的项目可使用 `View -> ViewModel -> Service -> Repository/Network`。纯展示交互直接在 View；展示状态与动作适配放 ViewModel；业务用例与数据访问由服务/仓库边界承载。已有 composable/store/application service 可承担对应职责，不强制新增同名文件。

View 不承担原始 HTTP、持久化或复杂跨模块规则；可以调用项目已有 composable/状态接口。ViewModel 不 import 具体页面或持有入口对象，Service 不 import UI。模型表达数据与不变量，UI 模型和协议 DTO 分别归属，不因都叫 model 就共用一个万能类型。

小模块可合并职责；仅在真实逻辑存在时创建 model/service/view/viewModel。不要生成每层只有一行转发的空壳，复杂度增加后再按边界拆分。

正例：页面绑定订单状态并发出提交动作，应用服务校验并提交，ViewModel 映射结果。反例：按钮组件自行读取令牌、改全局订单对象并导航，父级不知道发生了什么。

## ARCH-04 组件、状态和资源的所有权

| 范围 | 默认位置与责任 | 对外协作 |
| --- | --- | --- |
| 模块私有 UI | 业务模块已有 view/components | 只在该模块使用，不被其他 feature 深层导入 |
| 跨模块通用 UI | 已有公共组件层 | 参数输入、事件输出，不改调用者私有状态 |
| 产品壳与导航 | 入口/产品组装层 | 组合 feature，负责产品级路由与设备适配 |
| 模块私有资源 | 该模块资源目录 | 命名表达用途，不复制到所有模块 |
| 共享/产品资源 | 已有公共/产品资源入口 | 使用真实资源可见性，不依赖另一模块私有路径 |

同一业务状态只有明确的主数据来源。组件临时状态留在局部，页面状态按页面生命周期，跨页面状态才考虑共享；账户切换、退出与租户切换时的清理按真实业务要求验证。子组件通知状态所有者，而非直接改深层共享对象。

数组/对象更新方式由框架响应规则和消费者契约决定，不普遍要求每次深拷贝。异步返回、错误恢复、订阅/计时器清理及设备切换要有相关测试或实际交互证据。

## ARCH-05 模块公开入口与跨模块协作

每个模块的公开入口只导出需要的能力/类型，保留内部实现边界。入口文件叫什么由实际清单与构建确定，不强制所有模块都有小写 index；避免 `export *` 把内部类型和资源一并公开。

跨 feature 通过稳定公开契约、明确事件或产品组装协作；不要 import 另一个 feature 的私有页面、ViewModel、内部数据库或资源。使用事件时说明身份、载荷、失败与订阅清理，不为减少一次 import 新建全局事件总线。

核验构建图和 import 的实际目标，包括别名、深层路径和间接循环；仅目录名正确不能证明解耦。门禁有正例/反例和非空扫描证据后才可称已启用，否则记录为审查约束。

## ARCH-06 新模块与增量迁移

新模块按需求先定义职责与状态/数据契约，创建必要模型/服务/展示状态，再编写 UI 与私有组件；补资源、公开入口、依赖登记、路由和测试。只新增该功能需要的产品入口，不预生成手机/平板/手表全部目录。

迁移先记录旧路径与依赖，再定义职责映射，按模块移动并同步引用、路由与资源。每个可独立验证步骤运行受影响测试和构建，保持业务行为；结构整理、UI 重做与框架升级分别明确范围。确认不再使用才清理空目录/占位文件，不删除用户内容。依赖未变时不重新安装全部包。

发生模块增删、公共能力抽取、依赖方向、公开入口或路由变化时，同步项目画像与结构文档：真实路径、职责、消费者、接入步骤和已验证范围。文档使用相对路径与占位符，不记录账号、签名秘密、私有日志编号、机器路径或来源截图信息。

详细路径见 [仓库规则](repository-structure.md)，对象命名见 [命名与设计](naming-design.md)，迁移例外见 [变更管理](change-management.md)。
