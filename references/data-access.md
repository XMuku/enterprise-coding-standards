# 数据访问、约束与迁移

触发：服务端持久化、表/索引/字段、SQL、事务和迁移变更。先确认数据库、驱动、ORM、迁移工具及实际版本；只在客户端修改展示时不读取。通用 API/权限边界见 [契约与安全](contracts-security.md)。

## DB-01 模型与命名服务于契约

默认数据库标识符 snake_case，具体表名、复数、主键和前缀沿用项目。默认约束/索引名表达用途，如 uk_orders_tenant_request；长度、唯一作用域及命名限制按真实数据库验证。

约束：字段先确定业务含义、单位、精度、可空性和生命周期。ID 类型与序列化方式须兼容消费者，尤其不能让前端以不精确的数值表示大整数标识。

正例：金额的精确类型、币种和舍入规则明确。反例：用浮点数存结算金额；为了通过 NOT NULL 随便填 0 或空字符串，混淆缺失和有效值。

不是所有表都必须有逻辑删除、租户或审计字段；只有对应业务语义存在才引入。旧字段改名需同步映射、历史数据及消费者，不能仅改实体属性。

## DB-02 查询有边界，索引有依据

约束：SQL 值参数绑定；可变表名/排序字段使用允许列表，不把客户端输入当标识符执行。对分页、批量读取、批量写入和上传处理设置需求对应的边界。

默认查询所需字段，分页需要明确且稳定的排序；性能敏感查询用代表性数据和执行计划验证，不凭“加了索引”宣称变快。

正例：排序包含必要的唯一补充键，定义翻页一致性预期。反例：无排序无限查询；为每个字段建索引；循环内查询造成 N+1。offset/cursor、批量大小、索引顺序按数据库与访问模式选择，不一律指定一种方案。

## DB-03 并发约束在正确边界执行

约束：唯一性和库存等并发不变量不能只依赖“先查询、再写入”。依据一致性要求采用数据库约束、条件更新、版本校验或项目已有锁机制，并定义冲突后的业务结果。

正例：幂等键按业务与租户作用域唯一，重复请求返回约定结果。反例：应用先判断不存在就插入，假定并发不会发生；忽略影响行数；重试所有异常。

事务边界、锁顺序和回滚条件需在实际数据库路径验证。外部系统调用不要被误认为本地事务的一部分；跨系统一致性沿用已有方案，不自动引入复杂平台。

## DB-04 迁移兼顾旧代码、数据与回退

约束：使用既有版本化迁移流程；已在共享环境执行的历史迁移不直接改写。DDL 是否事务化、是否锁表和在线变更能力按数据库版本确认，不承诺任意数据库可自动回滚。

有滚动发布或旧客户端并存要求时，默认采用兼容扩展、数据回填、验证、切换、后续收缩的分阶段思路；各阶段保留旧版本可工作的条件。不要求小型单机项目机械套同样流程。

正例：新增字段先支持旧数据，回填验证后再收紧约束。反例：同次发布直接删除仍被旧实例读取的列；添加必填列却不处理历史行。

破坏性变更要说明影响数据、备份/恢复条件及执行边界；“回退应用版本”不等于恢复已删除数据。开发测试不执行生产迁移。

## DB-05 数据验证覆盖真实失败

至少按变更核验空库迁移、代表性旧数据升级、约束冲突、查询边界和事务失败路径。替身数据库与目标数据库存在差异时明确缺口，不用内存库通过替代所有方言、索引和锁行为验证。

具体命令从项目查证；可用 [测试规范](testing.md) 组织用例。没有目标数据库环境时标记未验证，不能通过关闭约束或删失败测试制造通过。
