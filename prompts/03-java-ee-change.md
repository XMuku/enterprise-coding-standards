# 03 Java EE / Jakarta EE 开发

与 [容器与命名空间规则](../references/java-ee.md) 配套。普通开发不自动迁移；明确的迁移可进一步选 [迁移提示词](09-refactor-migration.md)。

```text
按 enterprise-coding-standards 处理现有 Java EE / Jakarta EE 项目。
规范仓库：<KIT_ROOT>
项目：<PROJECT_ROOT>
需求与验收：<TASK>
本次是否明确要求迁移命名空间/容器版本：<默认否；如是，填写目标与范围>

先读取 SKILL.md、适用项目规则、画像、references/common.md 和 java-ee.md。
核对实际 JDK、容器及规范版本、Maven/Gradle 配置、WAR/EAR 形态、描述符、模块依赖。
确认项目实际使用的 Servlet/JAX-RS/CDI/EJB/JPA 等能力，不因为名称含 EE 就全量引入。
检查现有修改和同类代码，不替换为 Spring，不根据最新版网页擅自升级。

写入前确定：
- 变更所在模块/包/文件及依赖方向，公开组件、服务接口和 DTO 的真实职责与名称。
- 字段类型、单位、生命周期、线程访问、不变量与公开契约兼容性。
- 使用 javax 还是 jakarta 的具体 API 归属，以及容器提供依赖和应用依赖的边界。
- 注入/作用域/事务/安全上下文由谁管理，资源获取和释放责任在哪里。
- 对容器行为依赖的验收项及可用测试环境；不能把普通单元测试当部署验证。

实施规则：
1. 仅修改需求相关模块，保留现有容器管理机制，不手工 new 应由容器管理的组件来绕过机制。
2. 不在无明确安全保证的共享组件中存放请求级可变状态。
3. 核对连接/线程/事务等资源的容器约束，避免额外引入冲突 API 包。
4. 输入校验、身份与对象权限、异常映射和日志采用现有项目机制。
5. 没有明确迁移要求时保持现有命名空间与容器版本。

仅在迁移已明确授权时：
先列实际 API/第三方依赖/描述符/反射字符串/生成代码的兼容矩阵及消费者。
区分 Java SE 的 javax 包与需迁移的 EE API，不做全仓 javax 到 jakarta 字符串替换。
确认目标容器、构建插件、依赖范围和部署描述符相互兼容，分模块验证。
涉及不可兼容变化先确认过渡与恢复策略，不声称命名空间改完就迁移完成。

验证：
运行实际配置中的编译、测试、打包和适用静态检查，核对测试发现与有效断言。
容器启动、注入、事务、安全上下文和资源释放需要相应的容器集成证据。
若无可用容器，只报告已验证到哪一步和具体缺口，不连接或部署到生产环境。
最终说明变更、兼容矩阵变化、实际命令结果、未验证项及必要后续决定。
不提交、推送、发布，不因开发授权创建云资源或执行生产迁移。
```
