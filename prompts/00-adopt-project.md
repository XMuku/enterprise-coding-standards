# 00 首次采用项目规范

目标：先把规则变成项目能使用的入口，不在“采用规范”时偷偷重构或安装工具。复杂采用流程可参考 [完整流程](../docs/agent-workflow.md)，详细边界见 [采用说明](../references/adoption.md)。

```text
请在以下项目采用 enterprise-coding-standards，只落地规则文档，不改业务代码。

规范仓库：<KIT_ROOT>
业务项目：<PROJECT_ROOT>
已知目标与限制：<填写，未知的技术栈从项目核对>

1. 先读取规范仓库 SKILL.md，使用“采用”模式，再读取 references/adoption.md。
   读取业务项目适用规则、工作区状态、架构决策和必要构建/平台配置。
   不以当前终端所在目录代替我指定的业务项目，不覆盖已有修改。

2. 从真实证据识别各源码区域的语言/运行时、框架/容器、包管理器、ORM、目标平台。
   找到已有同类文件、源码根、测试根、生成目录、规则入口和真实检查命令。
   区分正式项目决策、既有实现和本包默认建议；不把一个遗留坏例子升为规则。
   不扫描任务无关的私人目录，不读取或复制密钥。

3. 仅选择项目使用的技术栈和公共专题，形成路径到规则的映射。
   创建前确认包/目录/文件/字段命名、接口与继承边界、错误/权限/数据契约。
   已有一致约定保留，未知关键事项列出可回答的问题，不编造团队共识。

4. 若使用 scripts/prepare-project.mjs，先预览，再在本次文档授权范围内应用。
   导出只生成候选文件；若文件已存在，不删除或强制覆盖以绕过冲突。
   改为比较现有文件并进行最小合并，保留项目定制规则。

5. 填写项目画像与检查计划：每个版本/路径/命令都有项目证据。
   将检查区分为已接入且已验证、已接入未验证、未接入、不适用。
   本次不安装依赖、不改 CI、不接入云服务，也不运行有外部写入的业务命令。
   没有证据的项保留待确认；不为了填模板引入数据库、租户或消息系统。

6. 已确认的精简约束可以合并现有规则入口，不重写无关约定、不创建 override 绕过它。
   关键选择未明确的内容保留候选状态，说明需要谁作出什么决定。
   只有画像关键项已确认、入口已合并、读取路径正确时才标记已采用。
   已采用不表示检查工具全部接入，也不保证所有 Agent 自动发现入口。

7. 校验生成/修改文件的本地链接、适用路径、真实命令和版本记录。
   交付文档位置、采用状态、尚缺决定、未接入检查与一条日常开发提示词。
   不把规范包自身 npm run check 的结果当业务项目检查结果。
   不提交、推送、部署或发布。
```
