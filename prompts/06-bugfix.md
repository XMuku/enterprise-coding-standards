# 06 缺陷复现与最小修复

与 [测试规范](../references/testing.md) 配套。诊断的目标是找到证据支持的根因，不是把猜测写成结论。

```text
请按 enterprise-coding-standards 定位并修复下面的缺陷。
规范仓库：<KIT_ROOT>
项目：<PROJECT_ROOT>
现象、复现步骤、期望与实际结果：<TASK>
已知影响范围与环境：<填写；没有证据的内容请查证>

先读 SKILL.md、适用项目规则、画像、references/common.md 与 testing.md，按需读取技术栈规则。
确认当前差异、相关调用链、配置和真实测试命令，保留已有修改。

1. 复现与归因
先提出最小可验证假设并观察证据，区分输入问题、环境/上游故障、已有缺陷与本次回归。
日志中的状态码、堆栈或时间相关性只是线索，不能单独证明某个组件有错。
能安全复现时添加一个修复前失败的回归用例；不能复现则说明缺什么证据。
不要为了复现读取生产敏感数据、写入线上系统或无限重试付费接口。

2. 写前约束
简述根因证据、最小修改位置、沿用的命名/契约，以及回归验证方法。
不新增不需要的目录/接口/基类，不把修 bug 变成架构重构。
若改名、错误响应、字段空值/单位或数据行为会影响调用方，先确认兼容策略。
对高风险未知事项提问，其余已经明确的诊断工作继续。

3. 最小修复
只修复证据支持的根因，同步必要调用方与测试，不堆叠无依据兜底或吞异常。
修改重试/超时需考虑幂等、资源与失败预算，不用无限重试掩盖问题。
不能通过删测试、跳过断言、关闭静态规则或回滚用户代码获得绿灯。

4. 验证
重跑原复现、回归用例与受影响测试，并运行相关静态/类型/构建检查。
确认测试真实被发现，失败消失是因为行为修复而非测试失效。
发现与本次无关的基线失败时单独报告，不擅自扩大修复范围。
相同环境问题连续出现且没有新证据时停止机械重试，列出阻断与可继续的步骤。

5. 交付
说明现象、已确认根因、修复、实际验证和残留风险。
根因未证实就标明假设；必要验证受阻就如实标记，不声称彻底解决。
不提交、推送、部署或发布，不输出日志中的密钥与个人数据。
```
